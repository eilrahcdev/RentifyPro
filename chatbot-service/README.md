# RentifyPro chatbot behavior and checks

Follow [the project setup guide](../README-SETUP.md) for dependencies, environment configuration, and the Node backend. This service uses the v6 dataset and supports English, Filipino, and Taglish replies. Questions about other languages receive an honest support limit.

Python owns question routing. It checks scope and private-record requests before brand or policy matching, normalizes common textese on a derived query, and returns structured intents. Node validates every primary and additional answer, supplies canonical policy replies, and reads current public vehicles or the authenticated renter's own booking records. Chat never approves bookings, records payments, bypasses verification, or edits listings.

Selected intents have optional `response_variants` in the existing v6 dataset. Each purpose has approved `en`, `fil`, and `taglish` responses. Python selects a `response_variant` such as walk-in `instructions`, `approval`, or `rejection`; Node validates that it belongs to the selected intent and serves its canonical text. Classifier text cannot override these answers, including reset and wellbeing variants. Older classifiers without a variant still receive the default response. The bounded conversation context may retain this purpose name and optional `requested_answer_type`, but never an approval result or payment amount. The answer type is one of `instructions`, `navigation`, `explanation`, `overview`, `troubleshooting`, `confirmation`, or `continuation`; Python and Node both reject other values. Older classifiers/clients may omit it. Short follow-ups use that context; explicit topic changes select the new topic. The request steps do not submit or approve anything on the user's behalf.

Accident and injury guidance puts safety and Philippine 911 emergency help first; damage disputes, lost keys, and suspected theft use Messages and Report issue once safe. Reschedule/shorten guidance states that no general edit control exists. Mileage, toll, parking, and fine terms remain conditional because there is no verified universal platform policy. Receipt guidance does not invent a download button. Expired or replacement IDs and identity corrections follow the existing verification review. General owner approval timing and rejection guidance is public; personal booking status remains session-protected.

The dataset covers payment troubleshooting, expired checkout, password reset, rejected verification and selfie checks, pickup location, rental problems, refunds, and owner listing, booking, and earnings guidance. Answers point to existing application controls. They do not promise payment success, a refund, approval, or private account values.

Up to three distinct answers can be returned in one message. Dependent vehicle-price clauses share validated search filters; payment and other independent clauses start their own task. Answers with different approved purposes remain separate. Follow-up context contains an intent, a topic, validated search filters, clarification metadata and candidate intents, bounded action flags, and up to three public brand/model choices. It carries no prices, renter IDs, booking records, or payment amounts. Every live-data follow-up retrieves current records again. Starting a new chat clears context; stored conversations retain the existing account scope and expiry.

The latest response intent describes that reply; `conversation_context.intent` describes the latest meaningful rental task. Brief acknowledgements, gratitude, and social replies retain that one task for at most two consecutive idle turns using a validated `idle_turns` integer. An ordinary low-confidence or nonsense fallback can also retain the task within the same two-turn limit. Security/scope rejections still clear it. A third social or fallback turn expires it; a meaningful answer resets the counter. Explicit topic changes replace it, while goodbye, explicit new-chat requests, and security/scope rejections clear it. Compound answers ending with gratitude retain the meaningful answer. No nested history or private account facts are accepted in context.

Full-message confirmation, explanation, and continuation expressions are checked before generic conversational matching in English, Filipino, and Taglish. `you sure?` qualifies the preceding policy or repeats a fresh lookup, `how?` selects the relevant instructions, and `and?` continues the task. `you okay?` answers wellbeing and retains the task. Acknowledgement aliases cannot partially match questions. Corrective phrases such as `I asked how`, `I said how, not if`, `Paano nga`, and `Hindi mo sinagot yung tanong ko` use the last valid task and requested answer type. Messaging corrections provide detailed real Chat Owner/Chat owner steps; `where exactly` gives navigation, and a non-response follow-up explains Messages and Report issue without promising an owner response time. An unspecified correction after an availability answer asks which information is missing. Without a meaningful context, short follow-ups and corrections ask which task the user means. Full-expression repair matching cannot override an explicit new topic. Existing missing-unit and missing-listing clarifications remain unanswered until the user supplies the required information.

The `topics` map in `chatbot_config.json` assigns all 61 intents to one of eight topic families. Clear questions use specific action routes and multilingual semantic matching. Ambiguous topic words receive a focused choice: for example, `payment` asks about methods, the down payment, or balance rules, and `methods` answers that pending choice. Explicit topic changes stop vehicle filters from carrying into payment or account questions. Replies such as `why?` and `tell me more` retain the relevant approved policy. English uses of `at` and modal `may` are distinguished from Filipino wording.

`unavailable?` without context asks whether the user means vehicles or a payment option. General inventory wording such as `unavailable vehicles`, `is there any unavailable vehicle rn?`, and `the unavailable vehicle listing` checks current counts without requesting a model. `which ones?` or `list unavailable vehicles` lists up to three matching public names and reports any remaining count. A numbered follow-up resolves only choices actually shown. Questions about a particular vehicle still need a name and clarify ambiguous listings. `why are unavailable vehicles hidden?` explains the page filter, while alternative requests search available vehicles. Status names have no booking buttons and never become unavailable booking recommendations. Payment-option availability answers do not claim a provider outage; they direct the user to methods actually offered in checkout and the existing payment-status and reporting controls.

Procedural questions such as `How do I browse vehicles?` serve approved instructions without an inventory lookup or recommendations. Concrete availability and price questions retain their live database paths.

Searches honor supported vehicle category, transmission, passenger count, budget unit, location text, and explicitly excluded brands. Location matching uses the listing's public location text. Non-place phrases such as walk-in payment, cash, balance, and vehicle categories stop location extraction. Broad car and truck filters use the existing type/subType taxonomy in `vehicle_category_subtypes`; sedan and pickup remain specific filters. A date phrase is preserved as a request, not interpreted as confirmed future availability. Users must select pickup and return dates and times on the vehicle page; existing booking checks remain authoritative. Unavailable units may be checked for public status but remain excluded from recommendations.

Rental duration (`duration_value` and `duration_unit`) is separate from passenger count. `motor` and `motorsiklo` mean motorcycle; cheapest searches sort actual comparable rates. Hourly listings can be compared with daily listings using the existing 24-hour conversion, which the reply labels when displaying daily equivalents. A budget without a unit still asks per hour or per day, retaining the original category, location, transmission, and other filters.

Validated vehicle follow-ups retain rental duration, requested dates and times, driver preference, and up to three public listing choices. Choices can include a public `listing_id`, which distinguishes two listings with the same brand and model. Rates and quotation amounts are never stored in conversation context. Relative dates use Philippine UTC+08:00 (`Asia/Manila`); schedule metadata never certifies bookability. Missing or contradictory listing specifications and unverified rates cannot be used to fabricate recommendations.

Price inquiries inspect current public inventory to distinguish unavailable listings from missing or restrictive-filter results. Total-price questions ask for a specific listing and duration when necessary. A verified quotation uses `backend/utils/pricing.js`, including booking creation's rounded hourly rates, exact rental hours, and the applicable driver rate. Complete pickup/return dates and times can supply the duration. A quotation reports the rental subtotal, excludes checkout fees, and never confirms a booking, payment obligation, discount, or deposit. Active booking locks and in-flight reservations keep vehicles out of recommendations. Complete, valid Manila schedules also check the booking controller's overlap predicate per answer. This read-only check does not reserve a vehicle or bypass eligibility and owner approval.

## Service access and local startup

Python requires `x-internal-key` on every HTTP endpoint except `GET /health` (and health HEAD probes). Node adds this header; guest website users can continue chatting through `/api/chat` without signing in. Missing/wrong keys are rejected before body parsing or inference. Metadata `/`, documentation `/docs`, and `/openapi.json` require service authentication too.

Set the same private `CHATBOT_INTERNAL_API_KEY` on Node and Python, or leave it blank in both to use their matching `INTERNAL_API_KEY`. The selected key must be at least 32 characters. A dedicated chatbot key preserves Face/OCR credentials. Keep keys out of frontend code and image builds; supply them through the service environment.

Node autostart inherits the backend environment. If you run Python manually, start from this directory with:

```powershell
.\venv\Scripts\python.exe -m uvicorn app:app --env-file ../backend/.env --host 127.0.0.1 --port 8001
```

Restart existing Node and Python processes after changing code or keys. Hosted deployments need matching service environment settings: deploy Node's header support before enforcing Python authentication. Keep `/health` as the hosting probe. `npm.cmd run services:check` from `backend/` also verifies authenticated metadata access and denial of unauthenticated metadata requests. Rate-limit defaults, proxy setup, and deployment boundaries are in [backend/ENVIRONMENT.md](../backend/ENVIRONMENT.md#api-request-budgets-and-chatbot-service-access).

From the repository root in PowerShell, run:

```powershell
cd .\chatbot-service
.\venv\Scripts\python.exe -B -m unittest test_chatbot test_service_security test_rental_conversations test_response_quality test_conversation_memory test_reliability test_conversational_repair test_assistant_offers test_search_relevance
.\venv\Scripts\python.exe -B evaluate_chatbot.py --json
.\venv\Scripts\python.exe -B evaluate_chatbot_holdout.py --json
cd ..\backend
node --test tests/chatbotDataset.test.js tests/chatbotResponseQuality.test.js tests/chatbotConversationMemory.test.js tests/chatbotConversationalRepair.test.js tests/chatbotAssistantOffers.test.js tests/chatbotRental.test.js tests/chatbotReliability.test.js tests/chatbotRouteIntegration.test.js tests/chatbotRenterStatus.test.js tests/chatbotRateLimit.test.js tests/apiRateLimit.test.js tests/chatbotServiceSecurity.test.js tests/chatbotAssets.test.js tests/chatbotProtection.test.js
```

For a machine with the model already cached, set `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` to avoid a model-download check during offline tests. First-time setup still needs the model download described in the project guide.

The holdout evaluator combines `chatbot_holdout.json` with `chatbot_coverage.json`, checks all 61 intents, and rejects exact normalized overlap with training examples or aliases. It reports results by topic, unnecessary clarification counts, and conversation turns. Its fixed public vehicle fixture includes an unavailable listing; classification and fulfillment are repeated to check determinism. Conversations replay the screenshot wording, clarification choices, topic changes, public listing choices, and new-chat resets. These are reviewed regression checks, not an estimate of every user's wording or a guarantee of exhaustive coverage. Route tests use isolated database fixtures and cover guests, owners, authenticated renters, revoked sessions, malformed secondary answers, booking locks, and injected context. Fixture checks do not prove payment-provider operation.

To check rendered conversations as well, start Vite on port 4176 and an isolated headless Chrome instance with CDP on port 9236. From the repository root, set the URL of a running Python classifier and run:

```powershell
$env:CHATBOT_CLASSIFIER_URL = 'http://127.0.0.1:8001'
node --env-file=backend/.env --experimental-websocket scripts/chatbot-focus-browser-check.mjs
```

The optional URL enables actual Python routing and Node public vehicle fixtures for every conversation in the coverage set. Without it, the script runs the original focus, draft, budget, date, and reset checks using its predefined responses. Browser fixtures do not access live renter records.

For the complete React > Node HTTP > Python offer tests, run `backend/scripts/chatbot-reliability-http-check.mjs <isolated-local-classifier-url> --serve` with a classifier configured with the script's fixture-only internal key. The script prints its `fixtureApiUrl`. Set `CHATBOT_API_FIXTURE_URL` to that URL and `CHATBOT_CLASSIFIER_URL` to the same isolated classifier, then run the browser check. Existing coverage uses its original public inventory snapshot; the new offer scenarios use the actual local HTTP route with isolated vehicle records and no database connection. These checks also cover sessionStorage reloads, new-chat resets, the two-idle-turn context bound, and the widget's 30-minute idle expiry. Stop only those test processes afterward.

Conversation state keeps `intent` as the last meaningful task; the current response still has its own `intent`. Optional `assistant_action` records the most recent meaningful response purpose: overview, instructions, navigation, explanation, troubleshooting, confirmation, continuation, or public vehicle search. `pending_offer` has exactly three string fields: `intent`, `action`, and `source_variant`. Its intent must match the task, its source must match the task's current variant (`base` for the default answer), and the approved dataset's `assistant_offers` map must declare that source/action pair. Only `instructions` for a supported instructions variant or `search` for `available_vehicles` can be offered. Node creates this field only after emitting the corresponding canonical offer text. Ordinary acknowledgements retain the task and offer for at most two idle turns; fulfillment, rejection, a new task, expiry, reset, and goodbye clear or replace the offer.

The existing context fields remain allowed: public entities and choices, task topic, approved conditions/candidates, clarification, response variant, requested answer type, and idle counter. Unknown fields and malformed nested state are rejected in both runtimes. Old contexts without the optional action/offer fields remain supported. This state is public guidance, never evidence of authentication, verification, booking approval, or payment. No history, private records, credentials, document data, or financial totals are added. Development route logs contain only approved identifiers, context outcome, and loaded asset hashes; production replies contain no diagnostic hashes.

The current Python routing revision is `search-relevance-limits-2026-10-12`. Its authenticated metadata reports both dataset and configuration SHA-256 values captured at startup. Node's dataset information reports its loaded canonical asset hashes. Synchronize assets with `node backend/scripts/sync-chatbot-assets.js`, verify with `--check`, and restart both runtimes together after installing this revision. Container builds must include `chatbot_conversation.py`; the Dockerfile already copies it. Approved response text uses the separate 4000-character response limit; the user message limit remains unchanged.

Bare categories such as `vans?` and `motorcycle?` search live listings. Explicit seating requests retain the category and minimum seat count; rental days remain duration. `pick up trucks?` searches the pickup subtype, while `pick up my truck tomorrow` gives pickup guidance. The optional public `vehicle_subtype` context field accepts only declared subtype labels compatible with its parent category. Big Bike is accepted as a specific listing label; existing fields cannot verify engine size, so other motorcycles are not silently substituted. Tricycle receives an explicit unsupported-search-category answer rather than a claim about current inventory. Questions about fitting people into an existing van retain passenger-capacity guidance.

With a valid task, `huh?` requests its explanation. A quoted acknowledgement question such as `what do you mean got it?` explains that acknowledgement without implying insurance, booking, payment, or account approval. Only three multilingual response variants were added; the existing intent/model thresholds are unchanged. The backend's dedicated burst/sustained/concurrency limits and frontend composer cooldown are documented in [backend/ENVIRONMENT.md](../backend/ENVIRONMENT.md#chatbot-request-budgets-and-shared-storage). The browser driver checks rate, network, and upstream feedback separately from actual Python/Node conversation checks, using a controlled clock for cooldown.

When extending coverage, add varied examples and reviewed responses for all three supported styles, cite the actual workflow in `policy_source`, and keep test questions separate from training examples. Add unrelated questions with similar words to scope tests. Keep live values out of fixed replies. Restart the Python service after changing the dataset, configuration, or routing code so startup indexes reload. Restart the Node backend after dataset or configuration changes because its canonical answers are cached. The Python `/` endpoint reports `routing_revision` and `dataset_sha256`; use them to confirm that the running service loaded the intended version. Normal startup commands are in the project setup guide linked above.
